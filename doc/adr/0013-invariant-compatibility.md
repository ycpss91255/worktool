# 0013 不變量 10：相容性

- 狀態：已採納（2026-09-29）
- 討論：#211（本 ADR）；定案於 #200（不變量第 10 條，2026-09-29 grilling）
- 對照：`ycpss91255-research/vendor_kit` 不變量 10

## 一句話

同一個大版號內不破壞原本的用法。

## 性質

worktool 的版本號是 `X.Y.Z`。

- 同一個 `X` 內，原本的用法持續可用：使用者照先前的方式下的指令，換到同一個 `X` 的新版本仍然照樣可用。
- 同一個 `X` 內，設定檔格式只加不改：新版本可以接受新的內容，但既有的寫法不改變意思、不被拒絕。
- 只有 `X` 變動時才可能不相容；不相容之前，先公告升級步驟。

適用範圍是 worktool 對使用者承諾的用法：使用者下的 `just` 指令與它們的選項、結束碼與錯誤訊息格式，以及使用者自己寫的設定檔（例如盒子清單）。開發約定不在範圍內（#200 定案 1：承諾對象只有使用者一種角色）。本 ADR 只寫性質；版本怎麼編、升級步驟在哪裡公告、相容性怎麼檢查，留給其他 ADR 或 issue。

## 為什麼固定

worktool 的主痛點是重建成本高（#200 定案 2）：換機、重灌時要整套重跑。使用者重建時靠的是自己先前的用法與設定檔；如果小版本升級就讓原本的指令失效、或讓原本的設定檔被拒絕，重建就會在最需要它的時候壞掉，而使用者事先沒有任何訊號。

違反的後果：

- 使用者不敢升級，只好停在舊版，之後的修正拿不到。
- 升級後才發現指令或設定檔不能用，得自己追查是哪裡變了、怎麼改，等於把升級成本轉嫁給使用者。
- 版本號失去意義：看版本號判斷不出這次升級安不安全。

大版號讓「會不會破壞」有一個看得見的訊號，公告升級步驟讓必要的不相容仍然有路可走。

## 目前由哪些機制或測試守住

先說結論：這條不變量目前**沒有**任何機制或測試直接守住。worktool 還沒有版本號（`doc/design.md` Open 項目 3 規劃首個對外版本為 `2.0.0`，於 M17 release），也沒有可以拿來比對的上一個版本。

下面的案例釘住的是**目前**的用法：用法一改，對應的案例會紅。但它們比對的是當下寫在 spec 裡的期望，不是上一個版本；改用法的 PR 可以同時改掉 spec，案例本身判斷不出這次改動是否跨了大版號。所以它們只算「用法改變時看得見」，不算守住本不變量。

- `test/unit/justfile_spec.bats` 「just box lists assemble, bench, default, enter, help (alias h), setup and status only」「just test <verb> forwards exactly --<verb> for every tier verb and build」：`just box` 與 `just test` 的指令集合是精確比對，少一個或改名就紅。
- `test/unit/assemble_spec.bats` 「an unknown option exits 2 with the documented message on stderr, nothing on stdout, and executes nothing」：未知選項的結束碼 2 與訊息格式。
- `test/unit/manifest_spec.bats` 「valid manifest (section + image) passes validation」：目前格式的盒子清單（區段名 + `image`）被接受。

待補：

- 版本號本身：`X.Y.Z` 記在哪裡、怎麼查（待補）。
- 與上一個版本比對的相容性檢查：拿上一版的用法與設定檔在新版上跑，同一個 `X` 內不得失敗（待補）。
- 設定檔格式「只加不改」的檢查：上一版的設定檔在新版上照樣被接受、意思不變（待補）。
- 大版號變動前公告升級步驟的機制（待補）。
